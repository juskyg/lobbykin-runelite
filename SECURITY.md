# Lobbykin · security and permissions

The plugin connects only to https://lobbykin.com/api/runelite/ using a revocable scoped credential. Credentials, pairing proofs and queued reports stay in memory; no secrets are stored in RuneLite settings, files, command arguments, URLs or logs. Restarting the client requires browser approval again. Disconnect clears local access; server-side access remains revocable on /runelite.html and expires after 30 days. The server stores only token hashes.

Browser connection: a click starts a five-minute request. The plugin generates a random token and separate verifier, sending only their SHA-256 hashes. The browser URL fragment contains a random request ID, never either secret. A signed-in user reviews the matching friendly device name and explicitly chooses optional scopes. Only the client with the verifier can claim approval; it already holds its own candidate token, so no raw credential is returned to the browser. Cancel/shutdown discards local state, timers and pending requests. An already approved link can be revoked on the website. Pending requests expire after five minutes; stored rows and start frequency are bounded.

Base session access returns up to 30 own active/scheduled sessions and private meeting/readiness details only where host or accepted. Hosts/accepted members also receive up to 100 accepted roster names, roles and Ready booleans, without participant account IDs. Pending applicants do not receive that roster. Refresh is every 30 seconds plus explicit actions. Reminders use already loaded session times. No additional HiScores calls are made.

Optional scopes default off and require explicit approval:
- Ready: own desired Ready boolean only, with authoritative host/accepted and active-session checks.
- Notifications: latest 20 own non-chat updates, respecting existing website notification preferences. Initial history does not spam alerts. Native alerts follow RuneLite notification settings.
- Raid reports: only after explicitly selecting a current CoX/ToB/ToA session; group ID, random attempt ID, character name, world, typed start/death/completion/interruption/heartbeat events, timestamps and timing provenance. No chat text is uploaded. Server requires matching host/accepted character and valid scope. Death signals are deduplicated and bounded; death is not completion.

The current website uses host-direct acceptance. Retired place offers remain disabled and cannot be re-enabled by the browser pairing UI or current server issuer. Existing codes keep their remaining permissions; there is no silent grant expansion. No Jagex, Discord or website-session credential reaches the plugin. Character names and public HiScores are not ownership verification.

Raid start is based on supported game-system signals and entry-state observation. CoX has a recognised start message; ToB/ToA still have HUD/party-state fallback and need mode-specific live validation. Completion needs a prior start and supported system-message signal. Player chat is ignored. Local ActorDeath plus a small system-message allowlist provide death signals without inferring the end of the raid. Exit/disconnect/world or character change never means success. Cross-client matching is a session/raid/world/90-second-entry heuristic, not a unique game-instance proof or official Jagex KC. It cannot establish participation of every roster member. No automatic achievements/rejections are based on it.

Validated events update a phase and bounded lease: active heartbeats extend five minutes, capped at six hours from an observed attempt start; completion grants up to fifteen minutes for the next attempt. This keeps genuinely tracked play visible past the nominal session deadline without retaining abandoned sessions forever. Group closure/cancellation still wins. Ordinary group edits cannot directly set derived phase/lease fields.

Hop-to is one explicit user action using RuneLite's world service and the game's world switcher. The plugin never hops automatically, bypasses game restrictions or suppresses game warnings. It excludes dangerous/special worlds, offline/full worlds and instanced areas. Requests are bounded to three interface-opening attempts within ten seconds.

Network calls are serialized/time-bounded, private responses are no-store, redirects are not followed and response/request sizes are bounded. The in-memory report queue retries transient failures with stable attempt IDs; stale reports expire after 9.5 minutes. Revocation discards local state. Reports interrupted by shutdown can be lost, causing stale/interrupted tracking rather than completion.

This document describes the plugin protocol and expected server checks, not a fresh production audit. Backend authorization, cross-client deduplication and expiry have not been re-verified against the deployed service in this preparation task. Live multiplayer testing is recommended follow-up validation; the owner has chosen to request Plugin Hub review without waiting for it. Cross-client completion deduplication must not be described as live-verified. Not submitted to Plugin Hub and not affiliated with or approved by Jagex/RuneLite.
